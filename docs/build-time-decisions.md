# Settings that can't change after the first apply

Several inputs and hardcoded values pick an AWS resource's shape once, at
create time. Changing them later forces AWS or the `aws` provider to
recreate the resource (data loss, downtime, or both), is rejected outright,
or is a one-way door. Plan or price around these before the first
`terraform apply`, not after.

Each row applies only when the module creates the resource in question:
the EKS rows need `create_eks = true`, the RDS rows `create_database =
true`, the ElastiCache rows `create_elasticache = true`, the S3 rows
`create_s3_bucket = true`, and the ALB row `create_ingress = true`. For a
layer you bring yourself, the same constraints exist, but they belong to
whoever manages that resource.

| Setting | Module input | Effect of changing later | What to do instead |
| --- | --- | --- | --- |
| EKS cluster name | `cluster_name` (`local.cluster_name` in `locals.tf`, used in `eks.tf`) | The EKS API has no rename operation; `name` has no update path, so changing it replaces the cluster, every node, and every workload on it. Several other names derive from it too: the S3 bucket name (replaced, see the S3 bucket name row) and the RDS identifier (renamed in place, see the RDS row). | Pick `cluster_name` before the first apply. Renaming means standing up a second cluster and migrating workloads, not an in-place change. |
| EKS cluster subnets | `public_subnets`, `private_subnets` (`vpc_config.subnet_ids`, `eks.tf`) | `aws_eks_cluster`'s `vpc_config.subnet_ids` is not itself ForceNew, so adding subnets later is a plain update. Removing a subnet the control plane's ENIs already occupy, or changing the VPC entirely, is not a supported in-place move. | Size the subnet list for the VPC's full life before the first apply. To move to a different VPC, stand up a new cluster and migrate; the existing `existing_eks_cluster_name` VPC postcondition (`eks.tf`) exists precisely because this module assumes a fixed VPC for the cluster's lifetime. |
| EKS Kubernetes service CIDR | Hardcoded: never set (`eks.tf` has no `kubernetes_network_config` block) | AWS's own docs on `kubernetes_network_config.service_ipv4_cidr` are explicit: "You can only specify a custom CIDR block when you create a cluster, changing this value will force a new cluster to be created." This module never sets the block, so AWS auto-assigns from `10.100.0.0/16` or `172.20.0.0/16`, and that choice is just as fixed for the cluster's life as an explicit one would be. | Confirm neither default range overlaps anything the cluster's pods need to reach before the first apply. There is no module input to pick a different range; a caller who needs one brings their own cluster via `create_eks = false`. |
| EKS API authentication mode | Hardcoded: `authentication_mode = "API"` (`access_config`, `eks.tf`) | AWS access-entry documentation states the transition is one-way: `CONFIG_MAP` → `API_AND_CONFIG_MAP` → `API`, never backward. This module creates clusters directly in `API` mode, so there is no `aws-auth` ConfigMap fallback to revert to if an access entry is ever misconfigured. | Get IAM principal access right before the first apply. The module grants cluster admin only to the principal that runs the first apply, through `bootstrap_cluster_creator_admin_permissions = true` (`access_config`, `eks.tf`), and creates no other access entries. Add `aws_eks_access_entry` / `aws_eks_access_policy_association` resources for other principals in your own configuration. Recovering from a lockout means fixing access entries through the EKS API, not moving back to the ConfigMap. |
| EKS secrets envelope encryption | `eks_secrets_encryption_enabled` (`eks.tf`) | AWS's own warning is explicit: "You can't disable secrets encryption after enabling it. This action is irreversible." The module's own comment adds that enabling it later on an existing cluster may additionally force cluster replacement, depending on the AWS provider version. | Decide before the first apply. The default is `true`; set it to `false` only to preserve a pre-existing unencrypted cluster's behavior, and treat flipping it on later as a cluster-replacement risk to test in a non-production cluster first. |
| Node group instance type and disk size | `node_instance_type`, `node_disk_size` (`eks.tf`) | The EKS `UpdateNodegroupConfig` API has no call that changes a running managed node group's instance types or disk size, and the `aws` provider marks both as forcing replacement of `aws_eks_node_group.n8n`. The module runs a single node group with a fixed name (`n8n-nodes`) and no `create_before_destroy`, so Terraform deletes the existing group before it creates the new one. Every pod on the cluster, including n8n and the cluster controllers, is down until the new nodes join and the pods reschedule. The module does not set `ami_type`, so EKS picks the AMI type and there is no input to change it. | Pick instance size and disk size from the [Examples](../README.md#examples) table before the first apply. If you must change them later, plan a maintenance window for a full outage. If you need rolling node changes without downtime, bring your own cluster and node groups with `create_eks = false` and replace node groups there yourself. |
| RDS engine | Hardcoded: `engine = "postgres"` (`database.tf`) | The `aws` provider marks `engine` as forcing replacement of `aws_db_instance.n8n`. Replacement means a new, empty database. The instance `identifier` (`n8n-postgres-${local.cluster_name}`) is different: the provider renames the instance in place, and the endpoint hostname changes with it. | The engine is fixed by the module, so this only matters if you fork it. A `cluster_name` change renames the database rather than replacing it, but it also replaces the EKS cluster; see the EKS cluster name row above. |
| RDS storage encryption | `db_storage_encrypted`, `db_kms_key_arn` (`database.tf`) | RDS has no API to enable or disable storage encryption on a live instance; the module's own comment in `database.tf` documents that flipping `db_storage_encrypted` forces `aws_db_instance.n8n` to be replaced. | Decide encryption up front. To add encryption to an existing unencrypted instance, snapshot it, copy the snapshot with encryption enabled, and restore from the encrypted copy into a new instance (see the `db_snapshot_identifier` input). |
| RDS subnet placement | `private_subnets`, via `aws_db_subnet_group.n8n` (`database.tf`) | Adding subnets to `private_subnets` updates the subnet group in place. RDS refuses to remove a subnet from the group while the instance runs in it ([AWS re:Post](https://repost.aws/knowledge-center/rds-db-subnet-group)), so dropping a subnet the database uses fails the apply. Moving the database to a different VPC is a snapshot-and-restore migration, not a Terraform update. | Confirm `private_subnets` cover the VPC and AZs you want this database to live in for the long term before the first apply. |
| ElastiCache topology (cluster vs. replication group) | `redis_high_availability_enabled`, `redis_transit_encryption_enabled`, `redis_kms_encryption_enabled` (`redis.tf`) | `aws_elasticache_cluster` and `aws_elasticache_replication_group` are two distinct Terraform resource types; a `moved` block cannot bridge them. Flipping any one of the three inputs from its default destroys the single-node cluster and creates a new replication group (or vice versa), dropping every queued Bull job. See README → "Switching topologies replaces Redis". | Decide HA, transit encryption, and the CMK up front if you can. If you must flip one later, treat it as a maintenance window: queued executions in flight at the cutover are lost. |
| ElastiCache transit encryption (`transit_encryption_enabled`) | `redis_transit_encryption_enabled` (`redis.tf`) | On `aws_elasticache_replication_group`, the AWS provider documents that changing this with `engine_version < 7.0.5` forces replacement; this module pins engine `7.1`, so the in-place `transit_encryption_mode: preferred → required` path applies instead (see README → "Adding TLS to an existing replication group"), but only once the resource already exists as a replication group. Enabling it for the first time on the default single-node `aws_elasticache_cluster` still means a replacement, because that resource type supports transit encryption only for Memcached, not Redis. | Enable it before the first apply if it is a known requirement, since the first flip always costs a replacement coming from the default topology. |
| ElastiCache at-rest encryption (`kms_key_id`) | `redis_kms_encryption_enabled` (`redis.tf`) | `kms_key_id` on `aws_elasticache_replication_group` is set only at creation; AWS has no API to add or change the encryption key on a live replication group. | Decide the CMK before the first apply. Changing it later means creating a new replication group and re-populating the queue from scratch (acceptable for n8n's Bull queue, since it is not a source of truth). |
| S3 bucket name | Hardcoded: `n8n-${local.cluster_name}-${account suffix}` (`s3.tf`), or `existing_s3_bucket_name` | `bucket` is documented by the AWS provider as "(Optional, Forces new resource)". Renaming always means a new, empty bucket; S3 has no rename API either. | Treat the bucket name as fixed once binary or execution data exists in it. To move existing data, provision a new bucket and copy objects (`aws s3 sync` or S3 Batch Operations), then cut `existing_s3_bucket_name` (or `create_s3_bucket = false`) over to it. |
| S3 bucket KMS encryption toggle | `s3_kms_encryption_enabled`, `s3_kms_key_arn` (`s3.tf`) | `aws_s3_bucket_server_side_encryption_configuration` can be updated in place, but switching re-keys only objects written *after* the change: every object already in the bucket keeps its original encryption until rewritten. **Changing `s3_kms_encryption_enabled` from `true` to `false` with the module-created key also schedules that key for deletion.** Objects still encrypted with it become unreadable while the key is pending deletion, and cannot be recovered after the 7-day window. See the [key survival checklist](./destroy-cleanup.md#key-survival-checklist) and README → "KMS key after `terraform destroy`" for how to keep or recover the key. | Decide the bucket's encryption posture before loading real binary/execution data. Never switch from `true` to `false` while any object still uses the module-created key; rewrite those objects first. Switching from `false` to `true` is safe, but budget a full object rewrite (copy-in-place) if existing objects must move to the new key. |
| ALB scheme (internet-facing vs. internal) | `ingress_scheme` (rendered by `locals.tf` into the Ingress's `alb.ingress.kubernetes.io/scheme` annotation) | An Application Load Balancer's scheme is immutable once created; the AWS Load Balancer Controller's only way to change it is to delete and recreate the ALB, which drops the DNS target the Route 53 alias record (or your own DNS) points at until the new ALB is provisioned and the record is updated. | Pick `ingress_scheme` before the first apply. To flip it later, expect a brief outage while the controller tears down and recreates the load balancer, and re-verify the DNS alias target afterward. |
| n8n encryption key | `n8n_encryption_key`, `n8n_encryption_key_secret_ref`, the `n8n_encryption_key` output | Not AWS-enforced, but changing the effective key makes every credential already stored in n8n's PostgreSQL database permanently unreadable. n8n's own docs describe this as the instance's master key, set once, that never changes. | Back up the generated key immediately after the first apply (`terraform output -raw n8n_encryption_key`), see [`docs/post-deployment.md`](./post-deployment.md). Never edit `n8n_encryption_key` on a deployment with existing data unless you are intentionally restoring that data's original key. |

This list covers module-level and AWS-level constraints only. It is not a
substitute for reviewing [`docs/customer-managed-infrastructure.md`](./customer-managed-infrastructure.md),
which covers the `create_<x>` / reference-variable convention for pointing
the module at infrastructure you already run instead of letting it create
these resources at all.

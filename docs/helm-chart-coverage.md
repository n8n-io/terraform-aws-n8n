# n8n Helm chart value coverage

This module deploys the [n8n Helm chart](https://github.com/n8n-io/n8n-hosting/tree/main/charts/n8n) via `helm_release.n8n` (`n8n.tf`) and sets a large fixed subset of the chart's `values.yaml` directly, driven by typed Terraform variables. This doc catalogs which chart values this module exposes, which it hardcodes, and which it leaves entirely untouched (chart defaults apply), so you know when you've hit the edge of what the module can do for you today.

This module targets chart **2.0 only**: no dual 1.x/2.x support. Chart 2.0 replaced the per-container `config.extraEnv`/`queueMode.workerExtraEnv`/`webhook.extraEnv`/`executions.extraEnv`/`s3.storage.extraEnv` lists and the `secretRefs.env` `N8N_HOST`/`N8N_PORT`/`N8N_PROTOCOL` keys with `env.<component>` maps rendered into per-component ConfigMaps and loaded with `envFrom` (n8n-io/n8n-hosting#250, decision `0012-env-as-per-component-maps.md`); every row below that used to point at one of those lists now points at the matching `env.*` map instead. See [Upgrading n8n](./upgrading-n8n.md) for the migration.

**Verified against chart version `2.0.0-rc.1`**, the module's `n8n_chart_version` default (`variables.tf`), published at the default `n8n_chart_repository` (`oci://ghcr.io/n8n-io/n8n-helm-chart`; appVersion `2.44.5`, n8n 2.x). As a release candidate rather than a numbered release, `2.0.0-rc.1` sits outside the chart-pin verification tiers in [docs/versioning.md](./versioning.md) until chart 2.0 ships a stable release. The coverage table below reflects `2.0.0-rc.1`'s `values.yaml` keys; the chart can add, rename, or remove keys between releases, so a row here can silently go stale if you bump `n8n_chart_version` without re-checking it. Before you bump the default, diff the two versions' `values.yaml` (`task chart-diff CANDIDATE=<new>`, or `tests/scripts/chart-values-diff.sh <new>`; it reads the current pin from `variables.tf`, runs `helm show values` for the pinned and candidate versions and prints a unified diff, needing only Helm) and update this doc's version line plus any affected rows in the same PR. `tests/scripts/check-helm-chart-coverage.sh` (`task chart-coverage`) fails if the version line and `variables.tf`'s default disagree, or if the pinned chart's `values.yaml` has a top-level key with no backticked mention in the coverage table or [Not currently configurable](#not-currently-configurable). Any mention in those two sections counts, including a passing reference in their prose, so the check cannot tell a real coverage row from an aside.

**What must change once chart 2.0 ships a stable (non-`-rc.`) release:** move `n8n_chart_version`'s default to that release, update this doc's version line and appVersion, and re-run `tests/scripts/check-main-chart.sh` / `tests/scripts/check-helm-chart-coverage.sh` to confirm the stable chart's `values.yaml` still matches what was verified here against `2.0.0-rc.1`.

**There is no generic raw-values passthrough.** The only general escape hatch is `n8n_extra_env` (`env.shared`), and it only reaches environment variables, not arbitrary chart values. If you need a chart key this module doesn't set and isn't an environment variable, you cannot reach it through this module's inputs: see [Not currently configurable](#not-currently-configurable) below.

| `redis.healthCheck.enabled/port` | Not exposed; chart default used, and that default flips from `false` to `true` in chart 2.0 (`values.yaml`), with no module input to hold it at the old value. With it on, workers (and main, in queue mode) set `QUEUE_HEALTH_CHECK_ACTIVE`/`QUEUE_HEALTH_CHECK_PORT` (`templates/_env.tpl`'s shared `chartEnv`, gated on `has component (list "main" "worker")`) and the worker process opens an HTTP health listener on `redis.healthCheck.port` (default `5678`, same as `service.port`) inside its own pod — no chart-managed Service exposes it, and nothing else in the pod uses that port, so there is no port clash. Main already serves `/healthz`/`/healthz/readiness` on its own app port regardless of this flag; turning it on for main only adds the same queue-health route onto n8n's existing listener, not a second one. See the `probes.worker.*` row above for how this flag changes worker probe behavior |
| *(no chart key)* Redis / Bull queue metrics | The chart ships no exporter and no `metrics`/`serviceMonitor` block, and n8n's own `/metrics` (`n8n_metrics_enabled`) does not report Bull queue depth usefully in multi-main, which is the topology this module deploys. `redis_exporter_enabled` deploys a `redis_exporter` beside the release instead (see `observability.tf`), reading the same endpoint and AUTH Secret the chart is given. Outside the chart entirely, like the module's Ingress and webhook HPA |
| `s3.enabled/bucket.name/bucket.region/auth.autoDetect` | Hardcoded `true` / module-managed bucket / hardcoded `true` (Pod Identity). `s3.enabled` alone selects the `s3` binary data mode; chart 2.0.0-rc.1 removed `s3.storage.mode` and fails the render if it is set |
| `s3.bucket.host`, `s3.storage.forcePathStyle`, `s3.auth.accessKeyId/secretAccessKeySecret` | Not exposed; not needed given `auth.autoDetect = true` |

## Not currently configurable

Chart features with **no path to configure them through this module**, not even via an environment variable: `commonLabels`/`commonAnnotations` (governance tagging), `extraObjects` (arbitrary extra Kubernetes objects rendered into the release), `networkPolicy`, `extraContainers`/`extraInitContainers` (sidecars), `imagePullSecrets`, `hostAliases`, `podLabels`, `podSecurityContext`/`containerSecurityContext` (per-role/per-container security context overrides), `nodePlacement` (per-component scheduling within the chart), `serviceAccount.automountServiceAccountToken`, `persistence`, `chartEnvOverrides.*`/`envFrom.*` (chart 2.0's own env escape hatches), and the chart's own `ingress.*` block (superseded by the module's own Ingress management).

If you need one of these, you currently have two options: fork/patch the chart values by managing your own `helm_release` instead of this module (losing the module's other wiring), or open an issue describing the use case.
